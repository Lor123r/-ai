# 0002 宁可明确失败，也不要让界面显示"已保存"而磁盘为空

## 现象

`src/main/storage/startup.ts` 在启动期打不开注解存档时，需要一个兜底实现。

直觉做法是回落到 `InMemoryAnnotationRepository`——它能让应用继续跑，
用户还能标注，看起来体验更好。

实际后果是：内存版的 `save` 会 resolve 并在内存里留下副本，于是渲染层的乐观更新
一路走通、界面如实显示"已保存"，而**磁盘上什么都没有**。用户很可能就此关掉应用，
整个会话的标注灰飞烟灭，且过程中没有任何提示。

## 根因

这是唯一一条"界面说存了、磁盘没有"的真实路径，而**渲染层权限内没有任何办法察觉到它**。

渲染层能看到的只有 `save()` 是否 resolve。内存版让它 resolve 了，
渲染层就失去了唯一的判断依据。所以这个谎必须由主进程在源头堵住——
渲染层没有能力自救。

## 结论

**降级实现必须让数据操作明确失败，而不是假装成功。**

`UnavailableAnnotationRepository` 的做法：五个数据方法（`listByBook` / `save` /
`saveMany` / `remove` / `removeByBook`）**全部抛错**，只有 `load()` 保持 no-op
（它的契约本来就是空操作，且在启动链上没有调用方）。

读也一起失败是有意为之：`listByBook` 返回空数组会让界面宣称"这本书还没有注解"，
那同样是假话（磁盘上可能正躺着一份读不出来的存档），还会把用户引向"重新标一遍"，
可重新标一样会失败。五个方法一致装死之后，整个功能一致地表现为"本次会话用不了"，
渲染层只要走它本来就有的失败与回滚路径即可。

判定方式：**降级实现里，任何会改变用户对"数据是否持久化"认知的方法，都不能 resolve。**

## 反例

不要用内存实现兜底持久化存储：

```ts
// 错：界面显示"已保存"，磁盘为空
const repository = new InMemoryAnnotationRepository()

// 对：明确失败，渲染层走它已有的错误路径
const repository = new UnavailableAnnotationRepository()
```

也不要只让写失败、让读返回空数组——那会把"存档读不出来"伪装成"还没有存档"。
