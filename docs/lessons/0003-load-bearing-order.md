# 0003 顺序有依赖的步骤要在代码里标注"承重"

## 现象

`src/core/services/importAnnotations.ts` 的 `planAnnotationImport` 有三步：

1. 把所有注解重定向到 `targetBookId`
2. 按 id 去重
3. 按容量截断

这三步的顺序**不能换**。换掉之后代码照样跑、测试可能照样过，
但上报给用户的计数会错——用户看到"导入 10 条"，实际只存进去 7 条。

`src/main/ipc/booksIpc.ts` 的 `removeBookWithAnnotations` 同理：
必须先删书、再删注解、最后删文件。

## 根因

这类顺序依赖是**隐性的**：每一步单独看都正确，只有组合起来才有约束。
它通常只存在于作者脑子里，代码里没有任何痕迹。

后果是：后来的人（或 AI）重构时按"看起来更合理"的顺序重排，
功能静默出错，而且**测试未必能发现**——如果测试只断言"导入成功"，
不断言具体计数，重排后测试依然全绿。

## 结论

**顺序有依赖的步骤，必须在代码里显式标注"承重"，并说明换序的后果。**

标注要包含三件事：
- 这是承重的（用词要显眼，如"顺序是承重的"）
- 为什么承重（换序会破坏什么）
- 换序的具体后果（计数错、数据丢失、还是报错）

判定方式：**如果一段代码的正确性依赖于语句顺序，而顺序本身在代码里看不出来，
就必须有注释。** 反过来，如果注释删掉后读者会自然地写错，这条注释就是必要的。

## 反例

不要写"按顺序处理"这种没有信息量的注释：

```ts
// 错：没说为什么，读者照样会重排
// 依次处理注解
redirect(); dedupe(); truncate();

// 对：说清换序的后果
// 顺序是承重的：必须先重定向再按 id 去重，否则同一本书的注解
// 会因为 bookId 不同而被当成两条，去重失效，上报的计数会偏大。
redirect(); dedupe(); truncate();
```

也不要依赖测试来守护顺序——除非测试明确断言了换序后会错的那个数字。
