# 0009 文档过大要拆分，文档结构本身就是接口

## 现象

本仓库 `README.md` 有 139.8 KB、14 章。

AI 无法一次装载它——只能先 grep 找标题，再用 `view_range` 分段读。
每次想查一个细节，都要先花一轮工具调用定位。

## 根因

文档是**给读者消费的接口**，而 AI 的上下文是有限资源。

单文件巨型文档的问题不是"内容不好"，而是**无法按需读取**：
读者（人或 AI）想要第 7 章的一个细节，却必须面对整个 139.8 KB。
对 AI 而言这直接体现为上下文被挤占，或者干脆读不进来。

## 结论

**文档超过一定规模就拆分，并让入口文件只做索引。**

判定方式：**如果读者无法在一次读取中拿到需要的内容，文档就该拆了。**
经验阈值：单文件超过约 30–50 KB 就该考虑拆分。

拆分方式：
- 入口文件（`README.md`）只放概览 + 指向各章的链接
- 每章一个文件，放在 `docs/` 下
- 文件名语义化，让读者能从目录名判断该读哪个

本仓库的 `docs/lessons/` 就是这个原则的应用：一条经验一个文件，
AI 可以只读相关的那几条，而不是装载整个经验库。

## 反例

不要把"内容全"当成优点而拒绝拆分：

```markdown
<!-- 错：139.8 KB 单文件，AI 读不进来 -->
README.md  ← 架构 + 数据模型 + 13 个流程 + IPC 契约 + 测试地图 + 迭代历史 + ...

<!-- 对：入口做索引，各章独立 -->
README.md          ← 概览 + 链接
docs/architecture.md
docs/data-model.md
docs/flows.md
docs/ipc.md
docs/testing.md
```

也不要拆得过碎——一个概念一个文件会让读者在文件间反复跳转。
按"读者会想一次读完的范围"来切。
