# 0022 点击分区要按「看得见的那块」算，不能按外层容器算

## 现象

用户反馈「阅读时不能向前翻页，得唤起底栏按钮才行」。

第一反应是手势没绑上，于是写探针去测。结果**点击和滑动都是好的** ——
在正文上点一下、划一下，章节确实会翻。代码没坏。

但把点击位置按正文列的百分比扫一遍，问题就露出来了：

```
frac=0.3  第 1 章正文 -> 第 1 章正文   ← 没动
frac=0.4  第 1 章正文 -> 第 1 章正文   ← 没动
frac=0.5  第 1 章正文 -> 第 1 章正文   ← 没动
frac=0.6  第 1 章正文 -> 第 1 章正文   ← 没动
frac=0.7  第 1 章正文 -> 第 1 章正文   ← 没动
frac=0.8  第 1 章正文 -> 第 2 章正文   ← 只有这里翻得动
frac=0.9  第 2 章正文 -> 第 2 章正文
```

**正文列中间 70% 全是死区。** 用户的手指落在正文上，十次有七次什么都不发生，
体感就是「翻页坏了」。

## 根因

分区拿**外层容器**的宽度当分母，而用户瞄的是**看得见的正文列**。

```
.reader__body    整窗宽，桌面 1087px
.reader__viewport  min(900px, 100%) 居中，桌面 900px，左边空出 93px
```

```ts
// 错：分母是 1087，但用户按 900 那条来瞄
const rect = container.getBoundingClientRect()
const ratio = (event.clientX - rect.left) / rect.width
```

点在正文列 70% 处，`clientX = 125.5 + 836 × 0.7 = 710`，
算出来 `710 / 1087 = 0.65` —— 落进中间死区。

**两个坐标系都没错，错的是拿 A 的分母去除 B 的分子。**
`clientX` 是视口坐标（这点没错，iframe 里也是），
但 `getBoundingClientRect()` 取的是外层那块，两者宽度不一样。

手机上正文列与外层同宽，这个 bug 不显形；桌面窗口越宽，死区越大。
所以它很容易在开发机上「看着是好的」。

## 结论

**点击分区必须用「用户看得见的那块」的 rect。**

```ts
const rect = (viewportRef.current ?? container).getBoundingClientRect()
const ratio = (event.clientX - rect.left) / rect.width
```

同时把死区收窄。`TAP_ZONE_RATIO = 0.3` 意味着中间 40% 不响应；
手机上正文只有三四百像素宽，死区就是一百多像素。0.4 把死区压到 20%，
左右各 40% 都能翻页，中间仍留得下唤出工具栏的位置。

**验证方式：按可见区域的百分比扫一遍，而不是只测一个点。**
只测 85% 会漏掉这个 bug —— 85% 恰好落在两个坐标系都算「右区」的区间里。
要挑**两个坐标系会给出不同答案**的位置（这里是 70% 和 30%）。

## 反例

不要用「外层容器」当可见区域：

```ts
// 错：外层是整窗宽，正文列居中且更窄，中间一大片会落进死区
const rect = container.getBoundingClientRect()
```

也不要靠「把死区调小」来掩盖坐标系错误：

```ts
// 错：治标。分区边界仍然与用户看到的正文列对不上，
// 只是错得没那么明显，换个窗口尺寸又会歪
const TAP_ZONE_RATIO = 0.45
```

更不要用 `window.innerWidth` 代替：

```ts
// 错：正文列有 max-width，窗口越宽偏得越多
const ratio = event.clientX / window.innerWidth
```

同类风险：任何「按位置分区」的交互 —— 点击热区、拖拽落点、
画布上的命中判定、虚拟列表的可见区间 —— 都要先问一句
「我拿来算比例的那个矩形，和用户眼睛看到的那个矩形，是同一个吗」。
