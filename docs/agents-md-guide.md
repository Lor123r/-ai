# AGENTS.md 写作指南

这份文档回答一个问题：**新项目开工前，`AGENTS.md` 该怎么写？**

它同时适用于人和 AI 阅读。对 AI 而言，`AGENTS.md` 是每次对话都会注入的上下文，
所以它的质量直接决定协作质量。

---

## 一、先明确 `AGENTS.md` 的定位

`AGENTS.md` 是**规则**，不是**经验**，也不是**文档**。

| | AGENTS.md | docs/lessons/ | README.md |
| --- | --- | --- | --- |
| 内容 | 必须遵守的规则 | 为什么这么定的经验 | 项目是什么、怎么用 |
| 形态 | 短，每次对话都注入 | 一条一文件，按需读取 | 按章节组织 |
| 变更频率 | 低 | 持续追加 | 随功能更新 |
| 读者 | AI（每次）+ 人（偶尔） | 人 + AI（按需） | 人（首次）+ AI（按需） |

**规则会被执行，经验会被参考，文档会被查阅。** 三者混在一起会同时削弱三种作用。

最常见的错误是把长篇论证塞进 `AGENTS.md`——那会挤占 AI 的上下文，
而真正需要它遵守的那几条反而被淹没。

---

## 二、唯一重要的判据：可判定性

写每一条约束时问自己：

> **AI 怎么知道自己违反了这条？**

答不上来，这条约束就是无效的。对比：

| 无效写法 | 为什么无效 | 有效写法 |
| --- | --- | --- |
| 保持代码整洁 | 无法判定 | 单文件不超过 300 行 |
| 注意分层 | 无法判定 | `src/core` 不得 import Electron / React / DOM / Node 内置模块 |
| 注意安全 | 无法判定 | 所有路径操作必须经过 `requireInside(root, target)` |
| 写好测试 | 无法判定 | 交付前必须跑通 `npm run verify`，任何一项红都算没做完 |
| 及时提交 | 无法判定 | 每次改动完成后必须创建一个 Git commit |

**判据：这条约束能不能被 grep、被编译器、或被测试判定？**

不能的话，它会被忽略——不是 AI 不听话，是它无法判断自己有没有违反。

---

## 三、按规模分档

差异不在"写多少条"，而在**用什么手段强制**。

### 档位 1：小项目 / 原型（< 5k 行，单人，无发布）

```markdown
# AGENTS.md

## 注意事项
1. 每次改动完成后创建 Git commit。
2. 改动后跑 `npm test`，全绿才算完成。

## 技术栈
（一句话：语言、框架、包管理器）

## 目录约定
（三五行说明哪个目录放什么）
```

**不要写架构红线。** 小项目里分层是负担，写了也不会遵守。
这个阶段唯一值得强制的是"提交"和"测试通过"。

### 档位 2：中型项目（5k–50k 行，有发布，长期维护）

在档位 1 基础上加：

```markdown
## 验证门禁
交付前必须跑通：`npm run verify`
它等于 `typecheck && test && e2e`。任何一项红都算没做完。

## 架构红线
- 依赖方向：A → B → C，反向依赖禁止。
- 边界：X 层不得直接访问 Y。
- 新增接口必须同时改 N 处（列出具体文件）。
- 数据写入必须原子（tmp + rename）。

## 经验库
见 docs/lessons/。踩到新坑追加一条。
```

**这是"架构红线"开始有价值的临界点。**
判据：**如果违反约束的代价是"以后很难改"而不是"现在跑不起来"，就值得写进红线。**

### 档位 3：大型 / 关键项目（> 50k 行，或涉及资金 / 隐私 / 合规）

在档位 2 基础上加：

```markdown
## 子 Agent 定义
（把审查职责拆成独立 Agent，各自只读）

## 变更流程
（哪些改动需要额外审查、哪些需要人工确认）
```

**这个档位才需要子 Agent。** 小项目里加子 Agent 是过度设计——
审查成本会超过被审查的代码量。

### 强制手段的可靠性排序

| 规模 | 强制手段 | 典型约束 |
| --- | --- | --- |
| 小 | 人的自觉 + 测试 | 提交、测试通过 |
| 中 | 编译器 + 测试 | 依赖方向、边界、原子写 |
| 大 | 编译器 + 测试 + 独立审查 Agent | 上面全部 + 变更流程 |

**核心规律：约束的强制手段越靠前（编译器 > 测试 > 人），越可靠。**

所以写约束时优先选"能让编译器报错"的写法。例如把环境相关参数设为必填，
就把人肉检查换成了编译器检查（见 [0001](./lessons/0001-required-param-over-default.md)）。

## 四、七条通用原则

不管什么规模，这几条都成立。

### 1. 每条约束都要能判定

见第二节。写完逐条自问"AI 怎么知道自己违反了"。

### 2. 只写 AI 猜不到的东西

- "用 TypeScript 写" —— 不用写，看文件就知道
- "Node 装在 `D:\tools\node`，不在默认 PATH" —— **必须写**，猜不到
- "本机是 PowerShell 5.1，不支持 `&&`" —— **必须写**，猜不到

**判据：AI 能不能从代码里推断出来？能推断的就不用写。**

### 3. 区分"必须"和"建议"

`AGENTS.md` 里只放"必须"。建议放 `docs/`。
混在一起会让"必须"贬值——**当所有事都重要时，没有事重要。**

### 4. 规则要短，理由要近

`AGENTS.md` 写结论，代码注释写理由。

```markdown
<!-- AGENTS.md：只写结论 -->
- 所有路径操作必须经过 `requireInside(root, target)`。
```

```ts
// 代码里：写清为什么
// 路径来自可被篡改的 library.json，所以边界校验之外还要校验归属，
// 否则书 A 的 filePath 可以被改成书 B 的文件。
```

**规则要短**（否则挤占上下文），**理由要近**（否则改代码时看不到）。

### 5. 用测试守卫 `AGENTS.md` 自身

文档格式错误不会被任何工具报出来，只会静默失效。

本仓库的做法：`tests/unit/repo/agentDefinitions.test.ts` 检查每个子 Agent 定义
都被 `AGENTS.md` 引用；`tests/unit/repo/lessons.test.ts` 检查经验库格式与索引一致。

**凡是"格式错了不会报错、只会静默失效"的约定，都值得用测试钉住。**

### 6. 从失败里长出来，不要预先设计

本仓库最有价值的一条约束（子 Agent 不能有 `Bash`）来自实测踩坑，
测试注释里写着：

> 实测过：具名子 Agent 拿不到 shell，声称有 Bash 的定义把「跑测试」「git commit」
> 写进流程后完全无法执行，只会产出看起来做完了、其实没跑过的汇报。

**新项目的 `AGENTS.md` 应该从 5 行开始，每次踩坑加一条。**
一上来写 200 行，其中 180 行是想象出来的约束，反而会淹没真正重要的那 20 行。

### 7. 想让 AI 主动做的事，必须给出可对照的触发条件

这是第 1 条原则最容易漏掉的应用场景。

"踩到新坑就记一条经验"看起来是条规则，其实**不可判定**——
AI 永远可以认为自己没踩到坑。实测结果就是：经验库建好了，然后永远是空的。

对比两种写法：

```markdown
<!-- 不可判定：AI 会永远认为自己没踩到 -->
踩到新坑时追加一条经验。

<!-- 可判定：AI 能逐条对照 -->
满足任意一条就要追加：
1. 你修掉了一个 bug，而第一次尝试的修法是错的。
2. 你发现某处写法与直觉相反，且不写下来下一个人还会踩。
3. 你因为缺少某条信息而做错了事。
4. 门禁红了，而红的原因不是本次改动引入的。

不满足以上任意一条时不要写。
```

三个要点：

- **触发条件要能被"事后对照"** —— 不是"觉得重要"，而是"发生了 X 事件"。
- **必须写明"不满足就别写"** —— 否则 AI 会为了显得有产出而凑数。
- **不要用门禁强制** —— 该不该记是判断题，机器判不了。硬判只会逼出凑数条目，
  反而稀释经验库。规则给 AI 判断依据，门禁给机器硬性检查，两者分工不同。

同样的写法适用于任何"希望 AI 主动做"的事：主动补测试、主动更新文档、
主动报告风险。**只要触发条件不可判定，这件事就不会发生。**

## 五、起步模板

新项目第一天，建议这样起：

```markdown
# AGENTS.md

## 注意事项
1. 每次改动完成后创建 Git commit。
2. 改动后必须跑通 `npm run verify`（= typecheck + test + e2e），任何一项红都算没做完。

## 环境前提
（Node 路径、shell 限制、平台差异——AI 猜不到的）

## 验证门禁
`npm run verify`

## 架构红线
（先留空。踩到第一个坑时再写第一条。）

## 经验库
见 docs/lessons/。踩到新坑追加一条，编号只增不改。
```

**注意「架构红线」是空的。** 这不是偷懒——
**第一条红线应该来自第一次真实的架构破坏，而不是开工前的想象。空着比写错好。**

## 六、推荐骨架

项目长到档位 2 之后，`AGENTS.md` 的章节顺序建议固定为：

```markdown
# AGENTS.md

## 注意事项          ← 2-3 条，最高优先级，不可协商
## 验证门禁          ← 一条命令 + "部分通过不算通过"
## 环境前提          ← AI 猜不到的运行环境信息
## 架构红线          ← 可判定的硬约束，每条一句话
## 经验库            ← 指向 docs/lessons/
## 子 Agent 定义     ← 表格 + 格式守卫说明（档位 3 才需要）
```

**「注意事项」只放 2–3 条。** 放多了会稀释。

## 七、常见错误

| 错误 | 后果 | 修法 |
| --- | --- | --- |
| 写"注意代码质量"这类无法判定的约束 | 被忽略 | 改成可 grep / 可编译 / 可测试的写法 |
| 把长篇论证塞进 `AGENTS.md` | 挤占 AI 上下文，重要约束被淹没 | 论证移到 `docs/lessons/`，只留结论 |
| 开工前写 200 行约束 | 想象出来的约束淹没真实约束 | 从 5 行开始，踩坑再加 |
| 约束和文档混在一起 | "必须"贬值 | 规则进 `AGENTS.md`，说明进 `README.md` |
| 文档格式没有守卫 | 静默失效 | 用测试钉住格式与交叉引用 |
| 给子 Agent 写 `Bash` 权限 | 声称跑过其实没跑 | 子 Agent 一律只读，命令交人类执行 |

---

## 八、一句话总结

**`AGENTS.md` 的价值不在于写得多全，而在于每一条都能被判定、且都来自真实的失败。**

写之前问自己：**AI 怎么知道自己违反了这条？** 答不上来的，删掉。

## 九、可直接复制的模板

[docs/templates/](./templates/README.md) 里有开新项目时可直接复制的文件：

| 文件 | 作用 |
| --- | --- |
| [templates/README.md](./templates/README.md) | 开工清单：复制什么、按什么顺序做、什么时候加什么 |
| [templates/AGENTS.md](./templates/AGENTS.md) | 规则骨架，含占位符与注释说明 |
| [templates/lessons-README.md](./templates/lessons-README.md) | 经验库写作规范 |
| [templates/lessons.test.ts](./templates/lessons.test.ts) | 经验库格式守卫测试 |

**复制的是格式与约定，不是内容。** 经验条目属于各项目自己，不要跨项目搬运——
经验的价值一半在上下文里，抽走就退化成空话。
